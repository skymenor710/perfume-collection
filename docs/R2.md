> **FASE 3.0 = implementação local e testes. Nenhum objeto foi enviado ao R2.** Não existe bucket, nenhuma credencial
> do R2 está configurada, `MEDIA_BACKEND` continua `local`, nenhuma referência do banco mudou e não existe

## 2. Chave por conteúdo

`p/<sha256 do arquivo>.<formato real>` — ex.: `p/66f8…edd1.webp`.

- **Identidade = SHA-256 dos bytes.** Nome, pasta e extensão originais NÃO entram.
- **Extensão pelos bytes** (`sniffImage`), nunca pelo nome: o mesmo WebP salvo como `a.webp`, `b.png` e `c.jpg` vira
  uma chave só, `.webp`. PNG de verdade vira `.png`.
- Só `p/` + 64 hexadecimais minúsculos + `.webp|png|jpg|gif|avif`: não há como formar `..`, barra extra ou caractere
  estranho (validado também no core, `CONTENT_REF`/`safeImageRef`).
- Determinística e estável: mesma foto, mesma chave, em qualquer computador e reinício.
- A chave é a prova: objeto cujo SHA-256 não bate com a própria chave é recusado.
- O **nome útil** original fica no mapa (`refs`), não na chave.

**Deduplicação.** `bottles/a.webp` e `media/b.webp` com os mesmos bytes → mesmo SHA-256 → mesma chave → **um objeto**,
duas referências no mapa. Mesmo nome com conteúdo diferente → chaves diferentes.

## 3. Mapa de migração (`data/media-map.json`)

```json
{ "version": 1, "updatedAt": "…",
  "objects": { "p/<sha>.webp": { "sha256": "…", "bytes": 1234, "contentType": "image/webp",
                                  "status": "validated", "validatedAt": "…", "storage": "r2" } },
  "refs":    { "bottles/x.webp": { "key": "p/<sha>.webp", "sha256": "…", "recordedAt": "…" } },
  "journal": [ { "at": "…", "kind": "cutover", "changes": [ { "productId": "…", "imageIndex": 0, "userId": null,
                                                             "field": "url", "from": "bottles/x.webp", "to": "p/<sha>.webp" } ] } ] }
```

- Só `status: "validated"` conta como migrado, e só é gravado **depois** de baixar o objeto de volta e o SHA-256 bater.
- `journal` guarda o lugar exato de cada troca feita no banco: a volta não depende do nome do arquivo.
- Arquivo ilegível ou fora do formato é **erro** (nunca "mapa vazio", que esconderia uma migração).
- Gravação atômica (temporário + rename) sob trava de arquivo (`media-map.json.lock`, trava de processo morto é
  retomada depois de 60 s). No Windows, arquivo sendo apagado/trocado por outro processo responde `EPERM`/`EACCES`/
  `EBUSY` por um instante: é tratado como "ocupado, tente de novo" (na trava, na leitura e no rename) — sem isso, um
  estresse de 8 processos × 40 gravações falhava em 4 de 5 rodadas; com isso, 5 de 5 completas. A suíte testa seis
  processos gravando ao mesmo tempo: nenhuma atualização perdida.
- Entra no `npm run db:backup` (`media-map.json` + SHA-256 no manifesto).

**Por que arquivo e não tabela** (ADR 0012): nesta fase o schema do Postgres não muda — uma migration pendente faria o
app recusar a partida, e aplicá-la no Neon não estava autorizado. A interface (`MediaMap`) permite trocar por uma tabela
na virada, para gravar referências e diário na mesma transação.

## 4. Upload com prova (`migrateObjects`)

Para cada conteúdo (uma vez por chave):

1. já `validated` no mapa **e** `exists` no destino → pula (sem upload repetido);
2. relê o arquivo; SHA-256 tem de ser o do inventário e o da chave (arquivo trocado = recusa);
3. `put` com o SHA-256 no corpo assinado (`x-amz-content-sha256`) e no checksum do servidor (`x-amz-checksum-sha256`):
   byte corrompido no caminho é recusado pelo R2;
4. `get` do objeto e novo SHA-256 — **HTTP 200 sozinho não é prova**;
5. só se `SHA original == SHA baixado == SHA da chave`: `validated` no mapa, com as referências antigas.

Falha em qualquer passo (indisponível, timeout, 5xx, upload perdido, interrompido, corrompido, objeto ausente) →
objeto **fora** do mapa, motivo no relatório, os outros seguem. Objeto com conteúdo errado sob uma chave por conteúdo é
removido (sem garantia; nunca é validado). Uploads simultâneos do mesmo conteúdo no mesmo processo esperam um único
upload; entre processos, o `put` é idempotente (mesmo conteúdo, mesma chave) e o mapa é serializado pela trava.

## 5. Dry-run

`npm run media:migrate` (padrão) — só lê: a coleção (Postgres só com SELECT, ou `library.json`, ou `--file=`), os
arquivos e, se o R2 estiver configurado, a existência dos objetos (`exists`; o tipo `RemoteReader` nem tem `put`).
Mostra total, SHA-256, chaves a criar, já validados, já no destino sem prova, duplicatas evitadas, referências que
mudariam na virada, faltantes e divergentes (SHA-256 ≠ o registrado no banco ou no mapa). Relatório em
`data/migrations/media/`. Sai com erro se houver faltante ou divergente.

Rodado na coleção real em 29/09/2026: **32 referências, 32 objetos únicos, 32 a criar, 0 faltando, 0 divergentes**
(26 `bottles/`, 6 `media/`, 1852,7 KB, webp/png).

## 6. Virada e volta (funções puras, tudo-ou-nada)

- `planCutover(biblioteca, mapa)`: cada referência local vira a chave validada. **Uma** sem prova → plano vazio e
  bloqueado (antes da virada, falha de upload = nenhuma referência muda, o app segue local).
- `planRollback(biblioteca, mapa, resolver)`: cada chave volta à referência de antes — pelo **diário** (lugar exato);
  sem diário, pelo mapa só se houver UMA referência antiga com aquele conteúdo (mais de uma = ambíguo = bloqueia, nunca
  adivinha). Exige o arquivo local com o SHA-256 da chave.
- `applyRefChanges`: aplica numa cópia e confere o valor de antes de cada troca (plano velho não sobrescreve nada).

Provado nas 32 imagens reais: virada completa (32 trocas) e volta pelo diário devolvem a biblioteca idêntica.
**Aplicar no banco não existe nesta fase** (FASE 3.2, com `db:backup` antes).

## 7. Servir, fallback, CSP, Open Graph, service worker

- A página continua sem conhecer o R2: `assetRef("p/…")` → `/p/…` no próprio servidor. Rota `/p/<sha256>.<formato>`,
  com a mesma regra de acesso de `/media/`:

| Modo | Objeto validado no mapa | Não validado |
|---|---|---|
| `MEDIA_BACKEND=r2` | 302 para `R2_PUBLIC_BASE_URL/p/…` | `MEDIA_FALLBACK=none` (padrão): **404 + log `media.not_migrated` (erro)** · `MEDIA_FALLBACK=local`: cópia local conferida pelo SHA-256 + log `media.fallback` (aviso) |
| `MEDIA_BACKEND=local` | cópia local conferida (é o caminho de volta sem reescrever o banco) | idem |

  Fallback nunca é silencioso nem automático: precisa ser ligado, e cada uso fica no log.
- **CSP:** no modo local, exatamente a política de antes. No modo r2, `img-src` ganha SÓ a origem de
  `R2_PUBLIC_BASE_URL` (https, sem credenciais, `?` ou `#` — validado no start).
- **Open Graph:** local → `origem/ref` como sempre; r2 + validada → URL pública do R2; sem prova → pelo servidor.
- **Service worker:** sem mudança. Só intercepta `/bottles/*` e `/media/*` da própria origem (cache com teto de 300);
  `/p/*` (redirecionamento para outra origem, resposta opaca) e a URL do R2 passam direto, pelo cache HTTP normal.
  Depois da virada as referências mudam de URL, então nenhuma foto antiga fica presa no cache do app.

## 8. Fotos novas, semente e limpeza

- **Fotos novas** (`saveBottleMedia`): modo local, como sempre. Modo r2: grava PRIMEIRO a cópia local
  `data/media/<sha256>.<formato>`, depois sobe e prova; referências `p/…`. R2 falhou → a importação falha, sem
  referência sem prova.
- **`seedUpgrades`** (atualização pela planilha, a cada partida) vê as referências pelo mapa: `p/…` que veio de
  `bottles/x` É `bottles/x`. Idempotente: aplicar e rodar de novo devolve vazio, inclusive com as fotos já migradas
  (3 execuções seguidas, modo r2 e local, nenhuma mudança, nenhum upload). Semente mais nova com foto já migrada grava
  a chave (não volta para `bottles/`); foto nova ainda não migrada grava a referência local uma vez e fica estável.
- **Limpeza de órfãos** (`media/gc.ts`): só no disco local, nunca no R2. A cópia local de origem de uma chave em uso
  conta como em uso. Mapa ilegível = limpeza não roda.
- `bottles/` continua no site (`apps/web/public/bottles`, servido como estático) e `research-seed`/`embed-provenance`
  continuam gravando lá: a semente é local por natureza; o R2 recebe as fotos pelo `media:migrate`.

## 9. Invariantes

1. Nenhuma referência aponta para objeto sem `validated` (virada tudo-ou-nada).
2. `validated` ⇒ o objeto foi baixado de volta e tem o SHA-256 da chave.
3. Toda chave em uso tem uma cópia local conferida (bottles/, media/ ou a cópia dupla das fotos novas).
4. O mapa nunca é "adivinhado": ilegível = erro; volta ambígua = bloqueio.
5. O modo local é idêntico ao de antes da FASE 3 (API byte a byte, CSP, fotos, service worker).
6. Nenhum segredo sai do `.env.local`.
7. Dry-run não grava no destino.

## 11. FASE 3.1 — conectar ao R2 de verdade (não iniciada)

Ação do dono (única que não dá para fazer daqui): criar a conta/bucket no Cloudflare e um token de API do R2 com
permissão **só neste bucket** (leitura e escrita de objetos), e o domínio público (`img.<domínio>` ou `r2.dev`).
Depois, sem mudar nada no app oficial:

1. `npm run db:configure`-equivalente para o R2: colocar `R2_*` no `.env.local` (nunca no Git), `MEDIA_BACKEND` continua `local`;
2. `npm run db:backup -- --label=backup-before-r2`;
3. `npm run media:migrate` (dry-run, agora consultando o bucket) → conferir;
4. validação real do provedor contra o bucket: um objeto de teste (put/get/HEAD/list/delete), assinatura aceita,
   checksum recusando conteúdo errado, URL pública servindo os mesmos bytes (SHA-256 pela CDN);
5. `npm run media:migrate -- --confirm` → 32 objetos provados, mapa gravado, **nenhuma referência alterada**;
6. conferir pela URL pública o SHA-256 das 32.

A virada das referências no banco e `MEDIA_BACKEND=r2` são a FASE 3.2, com aprovação própria.
